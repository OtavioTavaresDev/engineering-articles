Building Effective Detection Rules with Sigma and KQL

Detection engineering strategies for reducing noise and improving signal quality.

May 8, 2026 13 min read

Why Sigma Changes Detection Engineering

Sigma is a generic, open-source signature format for SIEM systems. Instead of writing separate rules for Splunk, Elastic, and Sentinel, you write one Sigma rule and convert it to each platform. This allows detection engineers to share, version, and test rules like software.

More importantly, Sigma forces you to think in terms of log fields, not vendor syntax. A rule for "PowerShell downloading a file" becomes portable.

Example Sigma Rule: Suspicious PowerShell Command

title: Suspicious PowerShell Download String
status: experimental
description: Detects PowerShell commands that download a file from the internet
logsource:
    product: windows
    service: powershell
detection:
    selection:
        ScriptBlockText|contains:
            - 'Invoke-WebRequest'
            - 'Net.WebClient'
            - 'Start-BitsTransfer'
    condition: selection
tags:
    - attack.command_and_control
    - attack.t1105
level: medium

KQL for Real-Time Hunting

Kusto Query Language (KQL) is used in Microsoft Sentinel, Azure Data Explorer, and Defender. It's optimized for time-series and large-volume log analysis. A typical hunting query for lateral movement: 

// Find Remote Desktop logins from unusual IPs
IdentityLogonEvents
| where Timestamp > ago(7d)
| where Protocol == "RDP"
| summarize SuccessfulLogons = count() by AccountUpn, IPAddress
| where SuccessfulLogons < 5  // Low volume, might be suspicious
| join kind=inner (
    IdentityLogonEvents
    | where Timestamp > ago(30d)
    | summarize Baseline = count() by AccountUpn
) on AccountUpn
| where SuccessfulLogons < Baseline * 0.1  // Significant deviation

From Rule to Signal: The Testing Loop

  1. Write the rule in Sigma or directly in your SIEM's language.
  2. Test against historical data (last 30 days) to measure baseline volume.
  3. Run in "log only" mode for a week — don't alert yet, just record.
  4. Tune false positives by adding exclusions (e.g., "known good process path").
  5. Enable alerts with a low severity, then increase as confidence grows.

Common Tuning Techniques

  • • Whitelist by process path: Ignore `C:\Program Files\LegitApp\*` if it's noisy but benign.
  • • Count thresholds: Alert only if same event occurs more than 5 times in 1 minute.
  • • Time-based suppression: Don't alert on administrative activity during business hours.
  • • Correlation with asset criticality: Alert only if the target is a domain controller or a finance server.
