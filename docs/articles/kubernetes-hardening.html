Kubernetes Hardening Beyond Defaults

Why default Kubernetes deployments expose far more attack surface than most teams realize.

May 3, 2026 15 min read

The Default Insecurity of "Vanilla" K8s

Kubernetes ships with security features — but almost all of them are disabled by default. A default cluster allows any authenticated user to read most secrets, run privileged containers, and potentially escape to the host. The 2026 K8s Security Report found that 84% of clusters in production had at least one critical misconfiguration.

This isn't FUD. Attackers are actively scanning for exposed kubelets, anonymous binds, and default service account tokens. Let's walk through the real hardening steps that move beyond the "CIS benchmark checklist."

RBAC: The First and Most Broken Layer

Most teams grant cluster-admin to a handful of users and call it done. But RBAC is granular — you can restrict by namespace, resource type, and verb. Start with:

  • • Denying get secrets to all but a specific CI service account.
  • • Using ResourceQuotas to limit pod creation in namespaces.
  • • Rotating service account tokens and disabling automount for pods that don't need API access.

Privileged Containers Are a P1 Finding

Running containers as root with privileged: true gives the container almost all host capabilities. A single RCE in that pod equals full host compromise. Use securityContext to drop all capabilities and add only the needed ones: 

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  capabilities:
    drop: ["ALL"]
    add: ["NET_ADMIN"]  # only if required

Network Policies: The Most Ignored Control

By default, all pods can talk to all other pods. A compromised workload can scan internal services, probe metadata endpoints, and pivot laterally. Implement default-deny network policies and explicitly allow only necessary traffic. 

kind: NetworkPolicy
apiVersion: networking.k8s.io/v1
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress

Admission Controllers for Enforcement

Admission controllers (like OPA Gatekeeper or Kyverno) let you enforce policies before a pod is created. Examples:

  • ✓ Reject any pod that requests privileged: true
  • ✓ Require image digest (not just tag) to prevent tag hijacking
  • ✓ Force runAsNonRoot on all workloads

Runtime Security: Falco and Beyond

Hardening configuration isn't enough — you need runtime detection. Falco monitors syscalls and container behavior, alerting on suspicious actions like unshadow execution or reverse shells. Pair it with a SIEM to investigate.
